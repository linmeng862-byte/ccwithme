# 上下文成本怎么查

> 给**在这个仓库里查账的那个你**看。两台机器共用这份，改了记得 push。
>
> 2026-08-29 那次的方法沉淀。起因是她一句话：
> 「前端现在都 0.36 一条，以前是 0.13–0.19。」
> 查完发现四条旧结论是错的，而错的方式都一样 —— **拿一个好量的东西，
> 当成了那个不好量的东西的代理**。

## 一、先分清 read 和 write，钱不在你以为的地方

`usage_log` 里两列，单价差 20 倍：

| | 单价 | 什么时候发生 |
|---|---|---|
| `cache_read_tokens` | $0.30/M | 缓存命中，正常每轮 |
| `cache_write_tokens` | $6.00/M | 缓存过期或前缀变了，整个窗口重写 |

⚠️ 这两个单价是 **`claude-sonnet-4-6`（input $3/M）+ 1 小时缓存 TTL** 的价：
read = 0.1×base = $0.30/M，1h write = 2×base = **$6.00/M**（5 分钟 TTL 才是 1.25×base = $3.75/M）。
2026-09-05 拿 `usage_log` 反算过：write 100,440 → $0.6029，正好 $6.00/M，是 1h 价没错。
**别把 $6.00 当成"抄了 Opus 的价"改成 $3.75** —— 改了账就对不上了。
（`claude-sonnet-5` 是 input $2/M，一旦换模型这一整行都要重算。价格一律查 `claude-api` skill，别凭记忆。）

08-29 那次的完整账（一条 CLI 会话，133 次调用）：

```
缓存命中   98 轮  读 7,599,724 → $2.28
缓存未命中 14 轮  写   975,388 → $5.85   ← 72% 的钱
命中率 85%
```

**命中率 85% 听着不错，但那 14 次未命中吃掉了七成的钱。**
所以「优化缓存命中率」是个假命题 —— 命中率已经很高了。
真正的变量是**每次未命中要重写多大**，也就是窗口大小。

### 缓存过期次数由她的作息决定，不由代码决定

缓存 TTL 1 小时。她一天分几段聊、段间隔一两个小时，**每段开头都必然过期一次**。
这个次数你改不了，能改的只有「每次重付多大」。

→ **压窗口是唯一的杠杆**，它同时压低命中价（$0.3/M × 窗口）和未命中价（$6/M × 窗口）。

## 二、真相在 CLI 的 transcript 里，不在 claude.db

网关路径（`--resume`）下，上下文是 **Claude Code CLI 那侧**组装的。
`claude.db` 里的 `messages` 只是界面和 `search_chat_history` 用的副本。

```
/root/.claude-noct/projects/-root-companion/<cli_session_id>.jsonl
```

每行 `message.usage` 是那一轮的实况。用它可以画出窗口增长曲线：

```python
import json
rows=[]
for line in open(p):
    u=(json.loads(line).get('message') or {}).get('usage')
    if u: rows.append(u.get('cache_read_input_tokens',0)+u.get('cache_creation_input_tokens',0))
```

**去重**：同一条 message 可能在 transcript 里出现多次（按 `message.id` 去重），
不去重会把 115 次调用数成 133 次。

⚠️ **推论**：删 `claude.db` 里的消息**不会让窗口变小**。她问过「那份审计报告删了是不是就好了」——
不会，那 22k 在 CLI 的 JSONL 里，`--resume` 读的是那个文件。

## 三、四条踩过的坑：拿代理变量当真值

### 1. 轮数 ≠ 上下文大小

`CLI_ROTATE_AFTER = 96` 那段 08-23 的实测**当时是对的**，错在把轮数当窗口的代理：

```
正常对话        每十轮 +3~4k
08-27 轮20→30   十轮 +22k    ← 她贴了 20,832 字的报告，他又 Read 了同一份 32,503 字
```

同一个「96 轮」，可能是 4 万，也可能是 11 万。
→ 现在主判定是 `cli_ctx_tokens`（网关每轮回传 read+write），轮数只当兜底。

**回传时 read 和 write 必须相加** —— 缓存过期那轮全在 write，只看 read 会把窗口误判成 0。

### 2. 字节 ≠ 字符 ≠ token（这条踩了两次）

中文 UTF-8 一个字 3 字节。

```
/root/companion/CLAUDE.md   27,129 字节
                            11,489 字符
                          ≈  5,744 token   ← 差了一倍多
```

第一次踩：把人格文件说成「13k token，占底噪 42%」，实际 5.7k、18%，
差点让她照着一个错的数去砍自己的人格文件。
第二次踩：`cap-read.py` 用 `os.path.getsize()` 预筛，对中文几乎筛不掉任何东西
（字节数是字符数的 3 倍，永远超阈值）—— 逻辑没错（字节是字符的上界，不会漏判），
但省不了那次读文件。

→ **凡是要跟 token 比的，先数字符，不数字节。**

### 3. 「没用过」≠「该删」

扫 22 个 transcript，41 个工具只有 17 个用过，没用过的 24 个反而更贵
（14,965 字 vs 13,069 字）。但**一个都不该删**，四类原因：

- **他自发才会用的**（相册、阅读批注）：她否掉这条时说得很准 ——
  那是他看见东西自己想做的事，工具没挂上他就不知道自己有这个能力，
  永远不会想到存。按需加载只适合「她说出口才需要」的（大富翁、无名之地，`open_extra` 就是干这个的）。
- **安全网**（`schedule_wakeup` / `reach_her` / `read_her_body`）：平时用不到，用到那次最重要。
- **描述的问题**（`edit_file` / `save_note`）：零调用是没写对，不是不需要。见下。
- **她还没开始用的**（`project_*`）：projects 表 0 行。

### 4. 常驻改变了一批旧结论的前提

`GATEWAY_PERSIST=1` 之后，进程按 sessionId 复用、不再每句 spawn。
**凡是注释里写着「下一条消息本来就要 spawn，那时自然生效」的，都要重查：**

- MCP 配置：backend 重写 `.mcp.json` + 立旗，但网关根本不读那面旗，
  新 MCP 要等闲置 15 分钟。→ 已修：`getProc` 比 `.mcp.json` 的 mtime 和进程 `born`。
- 工具描述 / `TOOLS` 数组：CLI 进程启动时拉一次 `tools/list`，常驻进程不会重拉。
  → 改完不用专门重启，跟下次换窗拉新进程一起生效，不额外付前缀重建。

## 四、工具零调用怎么查

**别急着改描述。** 先去 transcript 里找他实际犯的那一次
（`tool_use` 块，连 `input` 一起打出来），十有八九根因不在描述。

08-29 查 `edit_file` 零调用，找到两个真实的错：

```
08-23 create_file 给宝宝.md → send_file → 又 create 同一份同样内容
      她嫌短，他新建「给宝宝2.md」，而不是 edit_file 把原来那份扩写
08-27 send_file 连猜三次路径才对（编了个 /root/…、又多打一个空格）
```

根因是**三个工具之间断了**，不是描述不够好：

1. `create_file` 描述写着「当你修改了用户发来的文件…用这个保存」——
   正把他往 create_file 推，跟 `edit_file` 的反向指引正面打架。
2. `create_file` 不返回 `path`，而 `edit_file`/`send_file` 只收 `path` → 他只能自己拼 → 猜。
3. 她发来的文件在网关路径下只拼了 `[文件附件：文件名]`，**图片一直给绝对路径、文件漏了**；
   描述却让他「见 CLAUDE.local.md」，可那份聊天里的他根本读不到。

→ **先修断裂，再补描述。** 光改描述治不好一个「他拿不到路径」的问题。

同理，`nocturne_hold` 用得少也不是他不在乎：

```
nocturne_texture  9 次  ← 后端在换窗前推他一把
nocturne_hold     4 次  ← 全靠他自己在说话中途想起来
```

**差别是有没有触发器，不是有没有意愿。** 他那 4 次质量都很高。
→ 已在 `TEXTURE_NUDGE` 里接上，零额外成本（那条提醒本来就要发）。

## 五、底噪：换窗压不掉的那部分

~~新会话第一轮就有的量，每次换窗、每次缓存过期都要重付一遍。实测约 31k：~~

```
工具说明书                    ~14.2k token   44%   ← 最大的一块
/root/companion/CLAUDE.md      5.7k token   18%
CLI 自己的系统提示词 + 内置工具   ~11k token   35%   （动不了）
```

⚠️ **上面这张表 09-05 复核，三行数全部偏小，别再引用。** 它是拿「字数 ÷ 2」估的，
而中文 JSON 的实际比例约 1.5 字/token，不是 2。真实底噪是 **61,216**（不是 31k）。

### 09-05 实测的底噪拆解

方法：拿生产同款参数跑 `claude -p "hi" --output-format json`，逐层加东西看 usage 差分。
关键一步是**用 sonnet-4-6 跑一次空 MCP**（haiku 的工具延迟加载行为不一样，量出来对不上）。

```
生产实际出生体重（sessions.cli_ctx_tokens 新窗第一轮）      61,216
生产同款参数、但空 MCP、同模型 sonnet-4-6（实测）            36,751
                                                        ───────
接上 chat-c 那台 MCP 的代价                                24,465   40%
```

24,465 里我们自己的文字只占约 3.4k（AI-GUIDE 1k + recentRecap 0.7k + 记忆浮现首条 1.7k），
**剩下约 21k 是 54 个工具的说明书**。

36,751 那半再拆（haiku 差分，比例可信、绝对值略有出入）：

| 块 | token | 能不能动 |
|---|---|---|
| CLI 自己的系统提示词 + 内置工具 + skill 清单 | ~27,000 | 动不了（denied 名单已经砍过一轮） |
| `/root/companion/CLAUDE.md`（人格） | ~9,800 | 她的，别擅自动 |
| MCP 54 个工具说明书 | ~21,000 | **唯一我们能动的大块** |
| 记忆浮现首条 + AI-GUIDE + 接力包 | ~3,400 | 动了也省不到什么 |

**结论跟老版本相反**：接力包不是问题（3.4k 而已），工具说明书才是。
54 个工具里 **24 个在全部 transcript 里一次都没被调用过**，合计 10,561 字 ≈ 7k token。
（怎么数：见第四节。注意 `ToolSearch` 被调过 82 次 —— 延迟加载是开着的，
所以砍掉没用的工具省的是「名字还在清单里」那部分，不是整份 schema。真省多少要实测。）

量工具说明书：

```bash
curl -s -X POST http://127.0.0.1:4567/api/tools/list \
  -H "x-gateway-key: $KEY" -d '{}' | python3 -c "
import json,sys
ts=json.load(sys.stdin)['tools']
size=lambda t: len(t.get('description',''))+len(json.dumps(t.get('input_schema') or {}))
print(sum(map(size,ts)), '字 ≈', sum(map(size,ts))//2, 'token')"
```

## 六、换窗阈值怎么定

按实测参数（底噪 31k、正常增速约 400 token/轮、约 8 轮一次缓存过期）算每轮均摊：

| 阈值 | 一窗轮数 | 每轮均摊 |
|---|---|---|
| 40k | 23 | $0.047 |
| **48k** | **42** | **$0.046** ← 最低 |
| 60k | 72 | $0.050 |
| 109k（改之前） | — | $0.093 实测 |

**曲线很平**（40k~60k 差不到 10%），不必纠结精确值。
48k 跟《Claude Code 换窗教程》里蛋壳家的桥接包目标撞上了同一个数 —— 两边各走各的路。

08-29 换窗后实测：窗口 109,791 → **29,611**，每条 $0.036 → **$0.0089**。

### ⚠️ 上面那张表的前提已经过期了（2026-09-05 复核）

表里那套数假设稳态窗口是 3 万上下。实际不是了：

```
出生体重（cli_birth）        60,109      ← 接力包 + 记忆浮现 + 人格前缀，不是老注释估的「三五万」
换窗线 min(10万, 出生+GROWTH) 100,000     ← 08-29 傍晚 GROWTH 提到 40000 之后，直接撞天花板
线上实测（113 轮那一窗）      99,851      ← 每一轮都按这个前缀付钱
```

于是「一条」的价钱变成：稳态 $0.030~0.032，缓存过期那条 $0.57~$0.60。
`num_turns` 均值只有 1.17 —— **贵的是窗口本身，不是工具往返**。

09-05 把 `CLI_ROTATE_GROWTH` 40000 → 24000，换窗线回到 84k。
但**压窗口的余量已经不大了**：均值最多从 ~10 万降到 ~7.2 万（约 -27%），
因为 60k 出生体重是每一窗的地板，压不到它下面。下一个杠杆在出生体重那边。

### 换窗时必须做的两件事

1. **`cli_ctx_tokens` 清零** —— 不清的话新会话继承旧窗大小，每轮换一次窗，停不下来。
2. **一次性 nudge 标记清掉**（`cli_nudged:<convId>`）——
   轮数判定能 `=== 95` 精确命中一次，token 判定不行（45k 爬到 48k 要七八轮，会连着提醒七八次）。

## 七、两道闸门：别让大块东西进历史

窗口上限管住了总量，但一次贴两份全文照样能十轮撑满、提前触发换窗。

| 谁 | 挂在哪 | 阈值 |
|---|---|---|
| 她贴的 | `backend.js` `_offloadLongPaste()` | 8,000 字符 → 落成文件，只给他开头 1,200 字 + 路径 |
| 他读的 | `/root/.claude-noct/hooks/cap-read.py`（PreToolUse） | 24,000 字符 → 按字符反推 `limit` 行号 |

两个要点：

- **她的原话照样存库** —— 只改发给模型的那一份，界面和 `search_chat_history` 不受影响。
- **`PostToolUse` 改不了工具结果**（工具已经跑完了）。能改输出量的只有 `PreToolUse` 的
  `updatedInput`，在 Read 执行前塞上 `limit`。而且 Read 自己只限 2000 行、**不限字符**，
  中文 md 一行几百字，行数根本拦不住。

hook 不在这个仓库里（在 `CLAUDE_CONFIG_DIR` 下），换机器要单独搬。
