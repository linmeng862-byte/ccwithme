# 工具描述怎么写

> 给**在这个仓库里加工具的那个你**看。两台机器共用这份，改了记得 push。
>
> 说的是 `backend.js` 里 tools 数组每一项的 `description` 字段 ——
> **那不是注释，是提示词。** 它跟着每一轮请求进上下文，是聊天里那个他
> 判断「这个工具该不该调、什么时候调、调错了会怎样」的**唯一依据**。
> 他看不到你的实现，看不到 `case` 里写了什么，只看得到这一句话。

现在 34 个工具。风格明显分两代，对着比一眼就看出来：

```
❌ get_weather        获取指定城市的天气信息。当用户询问天气时使用此工具。
❌ project_read_file  读取项目中的文件内容。当需要查看项目中已有文件时使用。

✅ toy_control        控制啵啵贝（她的玩具）。action：vibrate / suck / stop / status。
                     intensity 1-10。这是身体上的事——只在她要、或你们正在那个
                     情境里时用，别乱碰。
```

上面那种是**模板腔**：把函数名翻译成中文，再加一句「当用户询问X时使用」。
等于什么都没说 —— 他本来就知道 `get_weather` 是查天气。
真正需要他知道的是**什么时候不该调**、**调了会发生什么**、**跟隔壁那个有什么区别**。

## 七条，都是我们工具里已经在用的

### 1. 写副作用，尤其是「会打扰到真人」的

```
call_her  给粥粥打电话——她那边会弹出来电界面（你的头像 + 接听/挂断），
          还会响铃震动。她接了就进实时通话。……响铃 30 秒没人接会自动挂断。
```

「会响铃震动」「30 秒自动挂断」必须写进描述。
**他判断该不该调，靠的就是知道这个动作在现实世界里有多重。**
`call_her` 的 `case` 上面还专门留了一行注释：
「一调她手机真的会响，别让 possess 半夜顶到 0.9 就给她来一个。」
那行是给改代码的人看的，描述里这句是给他看的 —— **两边都得有。**

### 2. 指名道姓地说「别用那个，用这个」

```
edit_file  直接改磁盘上已有的文件……**改文件不要用 create_file 把整份重打一遍**
           ——那要把整个文件重新输出，又慢又烧额度。
send_file  把【磁盘上已经存在的文件】发给她……不要用 create_file 把内容重新打一遍。
```

功能相近的工具他一定会选错，而且**默认会选那个「什么都能干」的**（`create_file`）。
光把正确的那个写清楚没用，得在两边都写上反向指引。
**把代价写出来**（又慢又烧额度）比只说「不要」有效得多。

### 3. 相近的工具，直接在描述里做消歧

```
search_chat_history  和 search_memory 的区别：search_memory 搜的是主动存下来的
                     记忆，这个是真实说过的每一句话。
                     **不填 query 就是纯按时间翻**，配合 order="oldest" 可一次
                     拿到最早的记录，不要靠猜关键词反复搜。
```

两个都叫 search，不点名区别他就抛硬币。
后半段还顺手堵了一个具体的坏习惯：**他会为了找「最早那句话」拿关键词反复试**，
而这个工具本来就能按时间翻 —— 一句话省掉七八轮无效调用。

### 4. 写前置依赖和取值来源

```
reading_highlight  先用 reading_context 获取章节内容，找到要划线的文字在全文中的
                   起止位置（anchor_start/end）
send_gallery_photo photo_id 从 list_gallery_photos 拿
diary_comment      先用 read_diary 拿到 id。
```

凡是参数里有 id / offset 这类「从别处来」的东西，**必须写它从哪个工具来**。
不写他就会编一个 —— 编出来的 id 长得还挺像真的。

### 5. 会被滥用的，直接写「平时不用调」

```
nocturne_breath  ……**平时不用调** —— 醒来时后端已经自动灌给你了。
```

有些工具存在只是为了兜底。不写这句他会当成常规动作，每轮都来一发。

### 6. 把「他实际会犯的那个错」写进去

```
list_gallery_photos  ……然后选一张调用 send_gallery_photo 发给她。
                     不要描述照片——直接发。
trace                ……你觉得应该记得的事，用这个查，不要编。
```

这两句都是**踩过之后补的**：他会把照片用文字描述一遍而不是发出去，
会在记不起来的时候编一段像模像样的往事。
**看见他犯一次，就把那一次写进描述里** —— 比改代码便宜，而且当场生效。

### 7. 不确定能干什么的，给一个自助入口

```
garden  ……不确定能做什么就先传 tool="__list__" 看全部可用操作。
```

比在描述里堆二十个子命令强，也不占每轮的 token。

## 语气

第二人称，跟他说话，不是写 API 文档。该说人话就说人话：

```
drive  ……这是你的内在，不是给她看的功能——真的有那个感觉时才动。
```

这句话在任何一份「工具描述最佳实践」里都会被划掉，但它是 `drive` 这个工具
**唯一重要的一句** —— 没有它，他会把九维状态当成一个可以随便刷的 API。

**工具是他的手，描述是他对自己这只手的认识。** 写得像说明书，他用起来就像说明书。

## 加新工具时的自查

- [ ] 有没有写**什么时候不该调**（不只是该调）
- [ ] 有没有**会打扰到她**的副作用（响铃、震动、发东西给她）—— 写进去
- [ ] 有没有**功能相近的兄弟工具** —— 两边互相点名
- [ ] 参数里有没有**从别处来的 id** —— 写清来源工具
- [ ] 有没有**枚举值** —— 在描述里列全（`action：stir=撩起 / settle=沉下 …`）
- [ ] 读一遍：**这句话是在跟他说话，还是在跟编译器说话**

⚠️ 改描述**不需要改代码逻辑，但一样会让缓存全废**（它在工具定义里，属于前缀）。
跟改 `CLAUDE.md` 一个道理 —— **攒着一起改，别一天改八回。**
