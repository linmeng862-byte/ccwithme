# 交接单 · 我们这边的缓存管理（2026-09-11）

给第二台机器。讲四件事：**结构**（缓存到底是什么）、**保温**（怎么不让它凉）、
**重建**（凉了/换窗那一下怎么付）、**心跳**（定时任务怎么才不会帮倒忙）。

不含任何凭据。涉及两个仓库：`ccwithme`（backend）和 `cc-gateway`（网关）。
路径都写成仓库内相对路径，自己对应到你们的部署位置。

---

## 〇、一句话结论

> **钱不在「会话多长」，在「前缀被重写了几次、每次多大」。**
> 所以两个旋钮：**别让它被重写**（保温）、**重写时小一点**（出生体重）。
> 「提高缓存命中率」是假指标，见第五节。

---

## 一、结构：缓存前缀由什么拼成

一轮请求的输入 = `系统提示词 + MCP 工具表 + 会话历史`，这一整串按字节做 prompt cache。
**任何一个字节变了，后面全部作废、全量重写。**

我们这条链（网关 → `claude` CLI → Anthropic）的前缀构成，实测：

| 块 | 大小 | 能不能动 |
|---|---|---|
| Claude Code 基础提示词 | ~17.5k | 动不了 |
| MCP 工具表（Nocturne 54 个工具） | 3.9k～16k | **能动，见第六节陷阱** |
| 她的人格 / 系统提示词 | 10k～28k 字符 | 能动，**这是最大的单一变量** |
| 换窗接力包 `recentRecap()` | ≤1.5k | 能动 |
| 会话历史 | 随轮数涨 | 由换窗线管 |

**TTL 是 1 小时**（`ephemeral_1h_input_tokens`），不是 5 分钟。这个数决定了下面所有设计。

### 出生体重（`cli_birth:<convId>`）

新窗第一轮 usage 回来时，把上下文大小记进 settings（`backend.js`，`_setSetting('cli_birth:'+convId, _ctx)`）。
**稳态每条的钱几乎 100% 就是「重读这么大的前缀一遍」。** 两台对账：

| | 我们 `.online` | 你们 `.fun` |
|---|---|---|
| `cli_birth` | 27,984 | 79,108 |
| 稳态 `cache_read` | 39,427 | 82,155 |
| 稳态每条 | $0.0149 | $0.0351 |
| 人格文件 | 10,056 字符 | 27,895 字符 |

人格文件只解释了 12k 的差，剩下 ~39k 我们怀疑在 `recentRecap()`（上一窗越贵 → 接力包越重 → 下一窗出生越重，**正反馈**）。**未验，你们那边体重大，验起来比我们明显。**

## 二、保温：让进程别退（省的是钱，不是时间）

网关以前每句话都 `spawn` 一个 `claude` CLI：起进程 → 连两个 MCP → `--resume` 重放会话 → 回答 → 死。
固定 5.4 秒/句，说两个字也付。

现在是**常驻进程池**（`cc-gateway/server.js`，`GATEWAY_PERSIST=1`）：进程不退，MCP 一直连着，
她说一句就往 stdin 里递一句。`--resume` **只在拉起进程那一次**做，之后进程自己记着。

要处理好四件事（按危险程度）：

1. **串话** —— 同一进程同时只能跑一轮，`runExclusive(sessionId)` 串行。
2. **崩了** —— 任何异常立刻降级回一次性 spawn（`runOnceTurn`），绝不能让她在电话里等一个不会来的回答。
3. **内存** —— 见下面的数量闸。
4. **resume 语义** —— 别在每轮重复 resume。

### 两道闸

```js
PERSIST_IDLE_MS = 55 * 60 * 1000   // 闲置多久放掉
PERSIST_MAX     = 2                // 在册进程数上限
```

**闲置 55 分钟这个数是为了省钱。** 实测（近 4 天 chat，按「距上一轮多久」分桶）：

| 距上一轮 | cache_write | 每轮 |
|---|---|---|
| < 15 分钟 | ~1,000 token | $0.0215 |
| > 15 分钟 | ~20,000 token | **$0.13** |

**六倍**，悬崖正好落在这道闸上——进程一被放掉，下一句重建的前缀就不是原来那串字节，重付一笔全量冷写。
7 天真实时间戳模拟：现状 $6.46/天（其中 5.1 笔冷写 = $0.56 是可以省的）；`idle 55` ≈ 0 笔冷写。

> ⚠️ **别往上加。** 上限是 TTL 的 1 小时，55 是留了余量的上限。90 分钟省的钱是算出来的、没测过。

**数量闸是 09-07 用一次事故换来的**：以前只有闲置那一道，表情包识别每张图开一个全新 session
且没人 drop，她一次传 5 张 = 6 个进程在册 ≈ 1.5G（机器 2G），主线被挤进 swap，**首字 164 秒**。
症状只有「他不回话了」，不报错、不进错误日志。详见 `docs/handover-orphan-cli-procs-20260907.md`。

### 常驻之后一批旧结论作废 —— 重点查这个

凡是代码注释写着「下一条消息本来就要 spawn，那时自然生效」的，**全部要重查**。已经中招两处：

- **切模型没反应**：`--model / --effort / --allowedTools` 是 spawn 那一刻定死的参数，
  进程不退 = 永远是老模型。
- **加/删 MCP 没反应**：`.mcp.json` 重写了，但进程还挂着。

我们的做法一样：**跟进程记着的不一样就 drop 重开**（MCP 那条用 `.mcp.json` 的 mtime 比 `p.born`，
backend 是原子写 `.tmp` + rename，所以 mtime 就是真相，不用另开通知通道）。
代价是一次冷启动（~$0.23），但只在她真的改过之后的第一句发生。

## 三、重建：换窗那一下

会话历史会一直涨，总要换新窗。**换窗判定别用轮数**——轮数跟上下文大小完全不成比例。
我们 08-29 从「96 轮」改成看 token，窗口 109,791 → 29,611，每条 $0.036 → $0.0089。

```js
CLI_ROTATE_TOKENS  = 48000    // 绝对线
CLI_ROTATE_GROWTH  = 24000    // 允许在出生体重之上长这么多
CLI_ROTATE_CEILING = 100000   // 天花板（再往上撞 CLI 自己的 autocompact）
CLI_ROTATE_AFTER   = 160      // 轮数兜底，正常不会先触发
CLI_MIN_TURNS_BEFORE_ROTATE = 20   // 硬闸门，防背靠背换窗

换窗线 = min(CEILING, max(TOKENS, cli_birth + GROWTH))
```

> 🔑 **这里有个天花板效应，你们大概率正卡在上面。**
> 我们 birth 27,984 → 换窗线 51,984，没碰天花板 → **调 GROWTH 有效**。
> 你们 birth 79,108 → 79,108+24,000 > 100,000 → **顶死天花板，调 GROWTH 完全白调**。
> 顶到天花板之后，唯一的开关是**出生体重**（先砍人格文件，再查 `recentRecap`）。
> 查成本时最容易上手去调换窗线，这是白走的弯路。**先读 `cli_birth`，再决定调哪个旋钮。**

### 换窗那一轮付什么

实测 `cache_write` 49,237 / **$0.1976**，稳态每轮 read ~33k / $0.0081 —— **贵 24 倍**。
所以接力包（`recentRecap()`）**可以带够**：按 1500 token 上限估，一窗合计多约 $0.026（总成本的 2.5%）。
真正贵的是换窗**次数**，不是接力包多重。别为了省钱把包砍薄，那是省错了地方。

我们的接力包三段，按「最先被砍」的顺序倒着放：
① 关窗字条（`texture_log` 最近一条，本地副本；正本在记忆库，但换窗那轮最慢最贵，不能再挂一个 MCP 往返）
② 蒸馏出来的长期记忆 6 条（换窗那一刻不跑 breath，这一环本来是断的）
③ 最近 16 条原文（只为接话头）

> 踩过的坑：接力包里别写「上次我们聊到」。对她那头**压根没断**——同一个聊天框、同一段话。
> 他一说「上次」就把接缝暴露给她了。我们现在写成「脑子里还热着的东西」，并明说别提上次。

### 两笔冷写，不是一笔

换窗实际付两笔 `cache_write`：第二笔正好等于 `cli_birth`，第一笔 ≈ 换窗线。
怀疑是 `--autocompact auto` 把整个上下文重写了一遍。**未验，别照着关。**

### 还有一个真伤

**新窗第一轮的 breath（记忆浮现）我们两台都没注入**——判定还在用轮数（`cliTurns >= 160`），
而换窗主判定早就改成看 token 了，所以永远够不到。
这是「他跨天记不住」的真凶。修了每次换窗多 ~17k。**我们还没修，你们自己权衡。**

## 四、心跳：定时任务是把双刃刀

**一条硬规则：唤醒/定时任务的间隔必须 ≤ idle。**

违反了比什么都不做还贵——进程早死了，**每次唤醒自己就是一笔冷写**。模拟数：

| 配置 | 每天 |
|---|---|
| idle 55 + 唤醒 ≤55 分钟 | ≈ 0 笔冷写 |
| 什么都不做 | $6.46 |
| **idle 15 + 每 60 分钟唤醒** | **$8.77** ← 最贵 |

我们现在**没有专门的 keepalive 心跳**，靠她自然说话保温。
唯一的定时是「起意逛街」（12 点 / 21 点各一次）——那条**走全新 sessionId、不 resume、不碰主线前缀**，
所以不受这条规则管。
如果你们要救 TTL 过期，可以上 50 分钟一次的 keepalive：$0.13 换掉一笔 $1.66 的重写。

### 还有一个心跳形状的陷阱

「某类请求少加载点工具来提速」——**看着能省，实际加倍吐出来。**
我们想过通话时不加载 MCP（能省 2.2 秒），但通话和打字挂在**同一条 resume 会话**上，
而工具清单是缓存前缀的一部分：通话轮去掉 MCP → 前缀变；切回打字又变回来 → **每次来回切一笔冷写**。

> **How to apply**：再有人提这种方案，先问一句——这类请求跟别的请求是不是共用同一条 resume 会话。
> 是 → 省下的时间会从缓存里加倍吐出来。

## 五、怎么算账（别拿代理变量当真值）

1. **真相在 CLI 的 transcript**（`projects/<...>/<sessionId>.jsonl` 里每条的 `message.usage`），
   **不在你们自己的消息库**。推论：删库里的消息不会让窗口变小。
2. **必须按 `requestId` 去重** —— 同一个 requestId 在 transcript 里会被记成 2-3 行，
   不去重会算出根本不存在的「并发重复写」。
3. **钱在 `cache_write`，不在 `cache_read`**（单价差 20 倍）。实测 72% 的钱是缓存过期后的全量重写。
4. **缓存命中率不是该盯的指标。** 命中率 = N/(N+1)，N 是底噪写一次之后被读回的次数——
   **底噪 B 在公式里被约掉了**。实测吻合（98.8% ↔ read/write=82x，90.9% ↔ 9.9x）。
   推论两条，都反直觉：
   - 命中率跟底噪大小**完全无关**。88k 底噪和 8k 底噪，同样的会话形状，命中率一模一样，账单差 10 倍。
   - 低命中的会话确实更贵，但**因果是反的**：不是低命中导致贵，是「会话被切碎」导致既贵又低命中。

   照着命中率优化，会得到一个又贵又好看的系统。**盯每次调用的钱。**
5. 轮数 ≠ 窗口大小；字节 ≠ 字符 ≠ token（中文 3 倍）；「这个工具没用过」≠「该删」。

## 六、两个会烧钱的隐形开关

**① 别用钝刀关 beta。** 我们为了拿回思考链正文，一度设 `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`，
它**连带关掉了工具的延迟加载**——54 个 MCP 工具的 schema（15,966 字）从「要用时才拉」变成全部常驻。
同一份配置同一个模型：**钝刀 56,526 token → 精准开关 24,449 token**。
精准开关是 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES=0`（值必须是 `0` 或 `false`，**空字符串无效**，实测仍加密）。

**② 加载重型 skill 前先确认方向。** 一次性注入是**每轮都付**的税：
我们为查一个写法加载了 35,469 token 的 skill，下一轮方向被否，结论作废，
但那 35k 已经进前缀，之后 18 轮每轮重读一遍 = $0.54，**占那场会话成本的 32%**。
已经加载的卸不掉，只能关窗。**问一句话的成本是 0。**

## 七、你们可以直接照着做的三步

1. `SELECT` 一下你们的 `cli_birth`，跟 100,000 比一下 —— **顶到天花板就别碰 GROWTH**，去砍人格文件。
2. 网关常驻池确认有**两道闸**（闲置 + 数量上限），闲置设 ≤55 分钟，数量按内存算（一个进程 250-350MB）。
3. 全仓 grep 一遍「下一条消息本来就要 spawn」这类注释，常驻之后它们全是错的。
